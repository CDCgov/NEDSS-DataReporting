reporting-pipeline-service · functional test audit

What the functional tests actually check, against what RDB_MODERN actually has

Every query.sql / expected.json pair in testData/functional was parsed and matched against the live schema of the RDB_MODERN database (pulled from the nbs-mssql container via docker compose). This is a coverage map, not a bug list — no test or fixture was changed. Some large gaps are expected and explained below.

Five things worth knowing before reading the table

Found while cross-referencing the fixtures against the live schema — none of these block the tests from passing today, but they affect how to read the coverage numbers below.

Wide, condition-driven tables skew the raw totals

14 tables have ≥100 columns — the LDF/condition-driven case-detail tables (DM_INV_STD, D_INV_RISK_FACTOR, D_INVESTIGATION_REPEAT, the *_DATAMART tables, etc.). Their column sets are dynamic per jurisdiction/condition, so no single fixture is expected to exercise most of them. They're flagged wide throughout — filter them out to see the coverage of the fixed-shape operational tables on their own.

Table name doesn't exist under that name

skipSupervisorReview/030 and 040 query [RDB_MODERN].[dbo].[LDF_DIMENSIONAL_DATA], but the live database only has S_LDF_DIMENSIONAL_DATA. Column names line up closely (case-insensitively), so it reads as a rename that the fixture didn't follow, not a different table.

Seven "nrt_*" tables aren't in RDB_MODERN at all

interview, authUserDirectWrite, providerDirectWrite, and morbidityReport query nrt_patient, nrt_provider, nrt_auth_user, and three nrt_interview* tables against RDB_MODERN.dbo — none exist there (checked sys.objects directly, not just INFORMATION_SCHEMA). These are almost certainly served from a different datasource at runtime (person-service owns Nrt* JPA entities of the same names), so they're excluded from the coverage table entirely rather than reported as 100% missing.

Five asserted column names don't match any live column

Five fixtures assert a field that isn't in that table's live schema at all — two are synthetic check labels, the rest look like drift:

F_STD_PAGE_CASE → CONDITION_CD LAB_TEST_RESULT → PROGRAM_AREA_CD D_VACCINATION → VACCINATION_ADMINISTERED_CD CONFIRMATION_METHOD_GROUP → ..._KEY_GT_1 (synthetic) BMIRD_MULTI_VALUE_FIELD_GROUP → ..._KEY_GT_1 (synthetic)

A handful of queries never test columns by design

8 of 847 query statements are row-existence or row-count sanity checks (SELECT COUNT(*) AS count, SELECT 1 AS something) against CASE_COUNT, L_INVESTIGATION_REPEAT, NOTIFICATION_EVENT, F_INTERVIEW_CASE, and F_PAGE_CASE. Excluded from "covered" counts below so they don't inflate them; it also means L_INVESTIGATION_REPEAT's 2 real columns are never checked by name anywhere in the suite.
